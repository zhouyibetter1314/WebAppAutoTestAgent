# Web应用自主测试智能体

## 典型场景与输入输出

用户输入网站地址、账号和自然语言场景，例如：
> 创建名为 Course Test 的项目，检查它同时出现在仪表盘和侧栏。

你的系统应自动完成操作，并输出：
- 结论：PASS、FAIL 或无法判定。
- 依据：每个检查点的预期、实际观察和截图。
- 执行记录：操作日志、Playwright Trace、耗时、步数和 Token。
- 使用入口：网页界面的输入、进度、历史与导出，以及命令行批量运行。

**有几个必须遵守的边界：** 模型固定为 deepseek-v4.1-flash，浏览器交互必须使用 Playwright，核心规划、执行、恢复和判定逻辑需要自己设计。禁止以 Codex、Claude Code、OpenCode 等现成 Harness 为运行基座，也禁止直接调用或封装 Browser Use。pi 虽未被点名，也属于现成 Harness，建议只参考设计。

## MVP

核心拆成五个模块：
1. 场景解析：把自然语言变成前置条件、操作目标和检查点，保留原始要求。
2. 规划：决定先做什么、需要什么证据，记录已完成与待完成事项。
3. 执行循环：读取页面的 DOM/ARIA 信息，让模型选择一个结构化动作，再由你的代码调用 Playwright。操作后重新观察。
4. 恢复与验证：定位失败时重新观察、等待或调整路径；验证时记录“预期、实际、证据”，逐项更新检查状态。
5. 报告：保存结论、截图、日志和 trace.zip，供界面查看与批量导出。

元素定位优先使用角色、名称和标签，例如 get_by_role、get_by_label。
Trace 可以记录浏览器执行过程，但你仍需单独保存检查点和判定依据，因为 SDK 的 tracing 不自动记录测试断言。

### 开发顺序

1. 部署指定版本的 4gaBoards，先跑通“创建项目并验证两个位置”的完整闭环。
2. 扩展到课程提供的 5 个 4gaBoards 示例，修复定位、重复操作和漏检问题。
3. 加上网页界面、历史导出和命令行批量入口。
4. 扩展拖拽、上传下载、权限与多账号场景，再覆盖 Admidio 和 Discourse。
5. 用失败案例做实验，比较通过率、误判、步数、耗时和 Token。

## 评测标准

> 结论正确 + 证据充分

单个场景通过需同时满足：测试结论与标准答案一致、执行轨迹满足必要证据规则、材料与执行步数符合要求。应用不满足场景要求时，智能体正确指出问题并提供证据，同样通过。

**场景通过率**（核心指标）

$$\text{场景通过率} = \frac{\text{通过评测的场景数}}{\text{总场景数}} \times 100\%$$

- 各场景等权，不因难度或应用类型加权。
- 可按「应用」和「难度」维度分别统计。

**不通过情形**

| 情形 | 说明 |
|---|---|
| 超出步数上限 | 超过该场景允许的最大步数 |
| 因执行错误未完成必要验证 | 必要检查点未被验证 |
| 结论为无法判定 | 未能给出 PASS / FAIL |
| 证据不足 | 缺少支撑结论的观察与截图 |
| 漏交材料 | 未按要求提交报告或轨迹 |
| 执行异常但已恢复 | 不判为不通过，按最终结论与证据评测 |

**提交物**

- 每场景判定报告、执行轨迹、页面证据、资源统计
- 完整源代码、依赖与运行说明、设计与实验报告

> 允许不同有效操作路径，不要求步骤与教师一致。
